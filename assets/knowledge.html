Apache HTTP Server

CVE-2026-119618 · mod_http2 堆内存破坏

Apache 于 2026 年 11 月 11 日披露，mod_http2 的 assign_headers() 在处理共享资源时同步不足，可导致堆内存破坏。外部流量能够到达受影响的 HTTP/2 处理路径时，可能造成进程崩溃或以 httpd 服务进程的权限执行代码。

受影响范围

上游 Apache HTTP Server 2.4.55–2.4.70 受影响，2.4.71 发布修复。独立发布的 mod_h2 2.0.8–2.0.42 也受影响。独立安装模块的实例应分别核对 httpd 和实际加载的模块版本，发行版回补以对应公告为准。

证据分析与复核

  • 网页线索保存 Apache 响应标识和本次连接协议。边缘代理协商出 HTTP/2 无法证明后端 Apache 也启用了 HTTP/2。一次 HTTP/1.1 响应同样无法覆盖其他虚拟主机或监听地址。
  • 主机核验先关联处理业务流量的 httpd 和 mod_http2.so，再核对对应虚拟主机的生效配置是否提供 TLS 下的 h2 或明文 h2c。磁盘上的 LoadModule 和 Protocols 仅是配置线索。只提供 HTTP/1.1 的实例不进入这条路径。
  • 修复复核升级至厂商确认的修复包，检查各实例重新加载后使用的程序和模块。暂时停用 HTTP/2 时，应核对所有相关监听地址和虚拟主机。

升级到修复版本

受影响实例应升级到 Apache HTTP Server 2.4.71 或该受支持分支的后续安全版本，也可使用发行版明确标注已回补 CVE-2026-119618 的更新包。单独安装的 mod_h2 应另外升级到厂商确认已修复的模块构建。

临时缓解

暂时无法升级时，在受影响的监听和虚拟主机中仅启用 Protocols http/1.1。逐个检查虚拟主机的覆盖项，确保 TLS 下的 h2 和明文 h2c 都已停用。业务允许时也可停用 mod_http2。

应用变更后，分别核查代理到后端及直连后端的协议。依赖 HTTP/2 的业务需要先验证兼容性。升级后重新核对运行中的 httpd 和实际加载的模块版本。

NGINX

当前专项按 CVE 分别评估。HTTP/2 流量控制问题会破坏内存，其余四项涉及释放后使用，即对象释放后仍被访问。是否暴露取决于运行构建和具体功能路径，某项命中只说明该项需要复核。

CVE公告描述上游范围主机复核重点
CVE-2026-123007HTTP/2 流量控制中的内存破坏1.9.5–1.31.8确认 NGINX 本身是否处理对外的 HTTP/2 流量。
CVE-2026-123633HTTP/2 释放后使用1.19.7–1.31.8核对实际配置中的 HTTP/2 上游路径。前端协商结果无法说明上游协议。
CVE-2026-123634解析器处理响应时释放后使用0.6.18–1.31.8核对运行时 DNS 解析器及引用它的代理配置。镜像等指令仅作为关联线索。
CVE-2026-121810HTTP/3 释放后使用1.25.0–1.31.8核对 HTTP/3、QUIC 监听和相关代理路径。响应中的协议声明仅表示服务宣告。
CVE-2026-113425邮件代理模块释放后使用0.5.33–1.31.8核对邮件代理监听、模块和 HTTP 认证服务配置。普通网页入口无法覆盖邮件服务。

升级到修复版本

NGINX OSS 受影响实例应升级到稳定分支 1.30.7、主线分支 1.31.9，或相应分支的后续安全版本。NGINX Plus 应升级到覆盖五项 CVE 的 37.0.8.1 LTS、37.3.0.1 CR，或 F5 确认包含修复的后续版本。发行版及其他衍生版本按厂商公告确认修复包。现场应按正在运行的 NGINX 映像和软件包完整修订号核对回补，并把磁盘配置关联到实际加载的站点或监听。SCTP 属于独立的内核核验项，可见性或禁载线索无法确认内核已修复。

临时缓解

  • HTTP/2（CVE-2026-123007、CVE-2026-123633）在受影响的 NGINX 监听上停用 HTTP/2。按版本使用 http2 off; 或移除 listen 的 http2 参数。调整前核对 gRPC 等依赖。
  • HTTP/3（CVE-2026-121810）停用受影响站点的 QUIC 监听，撤下对应的 HTTP/3 Alt-Svc 宣告，并核对实际 UDP 监听。
  • 解析器和邮件代理（CVE-2026-123634、CVE-2026-113425）暂时停用受影响的动态代理与镜像路径，或隔离相关入口。邮件代理可暂停对外监听，或将其访问限制为受信网络。保留这些功能时优先安排升级。

配置检查通过后再应用变更，并核对每个监听和上游实例。停用一种协议只覆盖对应路径。升级二进制后，执行适当的服务重启或二进制升级流程，确认旧 worker 已退出。

衍生版本与 Ingress

NGINX Plus 按 CERT-EU 披露的发行范围检查。F5 发布说明列出 37.0.7.1 LTS 和 37.2.0.1 CR 对 CVE-2026-123633 的修复，后续 37.0.8.1 LTS 和 37.3.0.1 CR 补齐另外四项。F5 Plus 发布说明。OpenResty 1.31.8.1 基于 NGINX 1.31.8，Tengine 3.2.0-rc5 的源码标注内核为 1.31.5。两者命中上游范围时需要核对厂商回补与实际组件。OpenResty 公告 · Tengine 标签源码

F5 NGINX Ingress Controller 5.7.1 使用 NGINX 1.31.8 或 Plus R37.2.0.1。5.8.0 的内核更新到 1.31.9 或 R37.3.0.1。集群巡检应按运行镜像中的实际版本复核。社区 ingress-nginx 已停止维护，仍在运行的实例应核对镜像内核并安排迁移。F5 版本矩阵 · Kubernetes 退役公告

Java / JVM

CVE-2026-114938 · HotSpot Base64 解码越界写

HotSpot 在 x86-64 上用于加速 Base64 解码的 AVX-512 intrinsic 存在边界检查缺陷，可造成堆缓冲区越界写。Oracle 记录的 CVSS 3.1 评分为 8.1。网络暴露还取决于应用是否把外部数据交给相关解码路径。Jenkins、Keycloak 等网页指纹只能提示可能使用 Java。

主机判据

  • 运行构建将业务进程实际映射的 JVM 库与对应运行时关联，再核对完整构建号、发行商和 VM 类型。PATH 的 Java 版本可能属于另一套安装。OpenJ9 不使用这条 HotSpot intrinsic。
  • 客户机 CPU核对 avx512f、avx512bw、avx512vbmi 和 bmi2。虚拟机以客户机可见能力为准。CPUID 与系统 flags 不一致时保留两份证据，工作负载迁移后重新评估。
  • 生效参数UseBASE64Intrinsics=false 或 UseAVX<=2 可阻断该路径。启动脚本、CLI 默认值和配置文件只能提供线索。需要确认时，可显式开启 JVM 诊断附加读取运行值。参数证据缺失时保留待确认。

临时缓解

暂时无法升级时，可在受影响的 HotSpot 服务启动参数中加入 -XX:-UseBASE64Intrinsics。在受支持的 x86-64 HotSpot 上，也可用 -XX:UseAVX=2 限制 AVX 等级。后者影响其他使用 AVX-512 的代码，应先评估兼容性和性能。

修改实际的服务启动配置并重启各实例，再核对 JVM 生效值。采集器启动的新 JVM 的默认参数，只能作为复核线索。

升级到修复版本

受影响实例应升级到所属厂商确认的修复构建。公开修复基线为 17.0.21.1、21.0.13.1、25.0.5.1 和 27.0.1.1。Oracle 另列出特定 Java 8 perf 构建。升级应按产品或 JDK 厂商公告确认完整修复构建，替换应用内嵌运行时或容器镜像并重启各实例，再复核实际运行构建。

PHP

网页可观察 PHP 版本与可选的上传相关线索。主机核验应确认处理业务请求的 Web SAPI、会话上传进度配置及厂商补丁。PHP CLI 的配置与版本可能不同。

CVE-2026-109618 · 内存耗尽后的状态破坏

PHP 在请求解析期间遭遇内存耗尽时，异常清理路径可能留下不一致的执行状态。实际影响须结合 Web SAPI、运行构建和发行版补丁核对。PHP 官方公告

CVE-2026-109619 · 陈旧的请求全局状态

请求生命周期结束后仍保留的全局状态可能影响后续请求。复核时应关注复用 worker 的服务部署和实际运行的补丁版本。PHP 官方公告

升级到修复版本

按实际运行分支升级到 PHP 8.2.35、8.3.36、8.4.27 或 8.5.12，或该分支的后续安全版本。也可采用发行版明确包含两个 CVE 修复的回补包。停止维护的分支应迁移到受支持版本。PHP 官方更新公告

临时缓解

业务允许时，在实际处理请求的 Web SAPI 中关闭 session.upload_progress.enabled。对仍需保留的上传入口，可按业务需要限制请求体大小，或限制入口访问。这些措施只缩小部分请求路径的暴露范围，两个 CVE 的修复仍需按 PHP 或发行版公告部署。

应用变更后核对实际 Web 或 FPM worker 的配置和版本。确认应用仍能正常上传，并检查各后端实例是否都已加载新配置和补丁。

研究的共同重点是：解析或错误处理被中断时，当前请求或复用 worker 中的状态是否仍被后续阶段使用。补丁因此不仅涉及会话功能，也涉及 OOM 处理、早期全局重置和 multipart 期间的对象行为。

五类利用链：前置条件、传播路径与防守点

A

会话写入 + 应用 LFI

前置：上传进度路径可写入会话，应用另有本地文件包含缺陷。

传播：上传元数据进入会话存储，应用随后包含相应会话文件。

防守：修复 LFI，隔离会话存储，禁止会话目录被 Web/PHP include。关闭上传进度只能减少这条路径。

B

反序列化清理重入

前置：攻击者能控制进入反序列化器的数据，并存在可触发的对象生命周期行为。

传播：失败或清理阶段发生析构重入，已释放的内部条目再次被访问。

防守：避免不可信反序列化，更新 PHP，审计对象析构与调用点；用 ASAN/崩溃栈复核，不能以普通 500 归因。

C

会话序列化处理器不一致

前置：同一会话在不同路径或请求中使用不同 serialize_handler，并具备对象链条件。

传播：一种格式写入的数据被另一种格式解释，失败清理仍可能触发对象生命周期。

防守：统一全部池、目录和虚拟主机配置；核对实际 Web SAPI，不能用 CLI 配置替代 Web 配置。

D

mod_php 解析期 OOM 与陈旧执行状态

前置：易受影响的 PHP 构建与 mod_php 生命周期，multipart 解析进入内存失败路径。

传播：解析被非局部跳转中断，关闭阶段继续读取不完整的执行器全局状态。

防守：安装完整补丁并重启全部 worker；关联 Apache/PHP 崩溃和请求日志。自查台不会主动制造 OOM。

E

FPM 跨请求陈旧反序列化状态

前置：同一 FPM worker 被复用，前一请求在会话解码期间异常中止，后一请求较早进入上传解析。

传播：后一请求在正常初始化前接触前一请求残留的反序列化状态。

防守：更新并重启 FPM 池；关联 worker PID、两次请求和错误日志。单次响应无法证明命中同一 worker。

链名称和根因模型来自下方 ikow 技术分析。页面省略载荷布局、内存地址推导、命令执行及故障注入步骤。

层面补丁或控制目的复核要点

可选“上传进度基础观察”只发送一次普通文本文件，不指定会话 ID、不回读文件。出现 PHPSESSID 也只记录为线索；没有 Cookie 也不能证明功能关闭。

在野情报与 IOC 的使用方式

EXPLOITATION.md 汇总时间线、公开研究、攻击模式、恶意软件活动、网络基础设施、文件哈希和请求特征。这些内容变化快，不能作为永久黑名单。应保留来源和观测时间，在 SIEM 中把异常 multipart、PHP/worker 错误、子进程、会话文件和出站连接关联起来；单个 IP、User-Agent 或默认字段名都可能被复用或修改。

本项目的处理

不把社区 IOC 内置为漏洞判定，也不自动拦截。管理员可将已验证的规则部署到现有 WAF/IDS/SIEM；上线前应做语法校验、TLS 可见性检查、请求体截断测试和合法上传误报基线。
